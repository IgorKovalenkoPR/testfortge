# Runbook — база даних на безкоштовному плані (E0.1′)

**Проблема, яку цей документ закриває:** безкоштовна база Render **протермінюється через 30 днів** після створення. Далі 14 днів grace, потім дані видаляються. Бекапів безкоштовний план не має жодних. Це вже спрацьовувало на цьому сервісі: БД переходить у «Suspended by Render», веб-сервіс не піднімається при старті, лікується видаленням БД і Manual Sync — тобто **втратою всіх даних**.

Для інструмента однієї людини це неприємність. Для платформи, де працюють команди, це неприпустимо.

**Рішення:** перевести `DATABASE_URL` на **Neon Free** — 0.5 ГБ, без терміну дії. Плюс власні бекапи, бо на безкоштовному плані їх не зробить ніхто інший.

---

## 1. Одноразова міграція на Neon

Коду це не коштує нічого: [engine/db.py](../../engine/db.py) уже нормалізує `postgres://` → `postgresql+psycopg2://` (`_normalize_url`) і приймає будь-який URL. Міграція — це заміна однієї змінної оточення.

### 1.1. Створити базу

1. Зареєструватися на neon.tech, створити проєкт (регіон — найближчий до регіону сервісу Render, щоб не платити затримкою за кожен запит).
2. Скопіювати connection string. Він має вигляд `postgresql://user:pass@ep-xxx.region.aws.neon.tech/dbname?sslmode=require`.
3. **`sslmode=require` залишити в рядку.** Neon без TLS не приймає з'єднання, і без параметра psycopg2 отримає відмову вже після деплою.

### 1.2. Перенести наявні дані

Якщо в поточній базі Render є дані, які треба зберегти:

```bash
pg_dump --no-owner --no-acl "$OLD_RENDER_DATABASE_URL" > dump.sql
```

```bash
psql "$NEON_DATABASE_URL" < dump.sql
```

`--no-owner --no-acl` обов'язкові: роль з Render у Neon не існує, і без них відновлення падає на кожному `ALTER ... OWNER TO`.

Якщо дані переносити не потрібно — пропустити цей крок, `init_db()` створить схему сам на першому старті.

### 1.3. Перемкнути сервіс

У [render.yaml](../../render.yaml) `DATABASE_URL` зараз береться з бази Render через `fromDatabase`. Для Neon це замінюється на керовану з дашборда змінну:

```yaml
      - key: DATABASE_URL
        sync: false        # значення живе в дашборді, не в репозиторії
```

`sync: false`, а не `value:` — connection string містить пароль, і в git він не потрапляє.

Зробити це **для обох сервісів** (`testfortge` і `testfortge-mcp`) — вони ділять одну базу.

### 1.4. Перевірити

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://testfortge.onrender.com/readyz
```

`/readyz` робить реальний `SELECT 1` через `engine.db.ping()`. `200` означає, що з'єднання живе. `503` — дивитися логи сервісу.

### 1.5. Прибрати стару базу

**Тільки після** того, як `/readyz` віддає 200 і дані видно в UI. Видалення бази Render незворотне.

## 2. Бекапи (обов'язково, не опційно)

Безкоштовні плани не дають бекапів, які можна відновити. Отже бекап робимо самі.

### 2.1. Що бекапити

Повний дамп. База маленька (див. оцінку обсягу в [cost_model.md](../plans/cost_model.md) §3) — вибіркові бекапи тут ускладнення без вигоди.

### 2.2. Куди

Cloudflare R2 (безкоштовно 10 ГБ, $0 egress). Дамп у кілька мегабайт стискається до сотень кілобайтів — місця з великим запасом на роки щоденних бекапів.

### 2.3. Чим

GitHub Actions на розписі. Безкоштовні хвилини, секрети вже є де тримати, і це єдиний планувальник у стеку, який не засинає:

```yaml
name: db-backup
on:
  schedule:
    - cron: "17 3 * * *"      # щодня, 03:17 UTC
  workflow_dispatch:           # і кнопка "запустити зараз"
jobs:
  dump:
    runs-on: ubuntu-latest
    steps:
      - run: |
          pg_dump --no-owner --no-acl "$DATABASE_URL" | gzip > backup.sql.gz
        env:
          DATABASE_URL: ${{ secrets.DATABASE_URL }}
      - run: |
          aws s3 cp backup.sql.gz \
            "s3://$R2_BUCKET/testfortge/$(date -u +%Y-%m-%d).sql.gz" \
            --endpoint-url "$R2_ENDPOINT"
        env:
          AWS_ACCESS_KEY_ID: ${{ secrets.R2_ACCESS_KEY_ID }}
          AWS_SECRET_ACCESS_KEY: ${{ secrets.R2_SECRET_ACCESS_KEY }}
          R2_BUCKET: ${{ secrets.R2_BUCKET }}
          R2_ENDPOINT: ${{ secrets.R2_ENDPOINT }}
```

`workflow_dispatch` тут не для зручності: без нього перший бекап станеться колись уночі, а перевірити відновлення треба **сьогодні**.

### 2.4. Перевірка відновлення

> Бекап, з якого ніхто не відновлювався, — це не бекап, а файл.

Раз на місяць, вручну, ≈15 хвилин:

1. Створити в Neon окрему БД (безкоштовний план дозволяє до 100 проєктів — саме для такого).
2. `gunzip -c backup.sql.gz | psql "$SCRATCH_DATABASE_URL"`
3. Локально запустити застосунок із `DATABASE_URL=$SCRATCH_DATABASE_URL`.
4. Відкрити проєкт, перевірити, що тест-кейси, чек-лісти й баги на місці.
5. Видалити тестову БД.

Якщо крок 3 або 4 не проходить — бекап зламаний, і про це треба знати зараз, а не в день аварії.

## 3. Життя з лімітом 0.5 ГБ

### 3.1. Скільки зайнято

```bash
psql "$DATABASE_URL" -c "SELECT pg_size_pretty(pg_database_size(current_database()));"
```

Найбільші таблиці:

```bash
psql "$DATABASE_URL" -c "SELECT relname, pg_size_pretty(pg_total_relation_size(relid)) FROM pg_catalog.pg_statio_user_tables ORDER BY pg_total_relation_size(relid) DESC LIMIT 10;"
```

### 3.2. Чого очікувати в топі

`server_session` — принаймні до виконання епіка E3. Сесія сьогодні тримає весь пак тест-кейсів проєкту; 60 TC — це близько 300 КБ **на сесію**. Саме тому [engine/server_session.py](../../engine/server_session.py) пише попередження `PAYLOAD_WARN_BYTES` із назвами найбільших ключів. Якщо в логах воно з'являється часто — це не шум, це попередження про заповнення бази.

`audit_log` зростає монотонно. Retention для нього — частина E8.5.

### 3.3. Чого в базі не має бути ніколи

Скріншоти, відео прогонів, Allure-бандли, завантажені файли. Усе це — R2. Один скріншот важить як 300 тест-кейсів.

## 4. Коли база засинає

Neon на безкоштовному плані призупиняє compute при простої. Перший запит після паузи додає 1–2 секунди. Це збігається з холодним стартом самого Render-сервісу (30–60 с), тож на практиці окремо не помітно.

Порядок дій **не** такий: «пінгувати базу щохвилини». 100 CU-годин на місяць — це квота, і штучне утримання compute живим її з'їдає. Пінгувати треба веб-сервіс (UptimeRobot, кожні 5 хв у робочі години), а база прокинеться сама з першим справжнім запитом.

## 5. Аварійний сценарій: «сервіс не піднімається, в логах помилка БД»

1. `curl -s -o /dev/null -w "%{http_code}\n" https://testfortge.onrender.com/readyz` — підтвердити, що це справді БД.
2. Дашборд Neon → чи проєкт живий, чи не перевищено квоту.
3. `psql "$DATABASE_URL" -c "SELECT 1"` з локальної машини — відділити «база мертва» від «сервіс не може до неї дійти».
4. Якщо база жива, а сервіс ні — перевірити, чи `DATABASE_URL` на сервісі не було затерто Manual Sync (саме тому в §1.3 стоїть `sync: false`).
5. Якщо база мертва — відновлення з R2 за §2.4, кроки 1–3, потім перемкнути `DATABASE_URL` на відновлену.

`init_db()` спроєктований під цей сценарій: він публікує `_engine` лише **після** успішного `create_all`, тож недоступна при старті база не залишає напівзібраний engine — наступний ленівий виклик повторить підключення. Тобто сервіс сам підніметься, коли база повернеться, без редеплою.
