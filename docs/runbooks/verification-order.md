# Чек-ліст перевірки функціоналу — в якому порядку і чому

Порядок тут не адміністративний. Кожен рівень **робить наступний
осмисленим**: якщо впав попередній, наступний або не запуститься, або
збреше — покаже зелене на тому, чого не міряв. Тому правило одне:

> **Не переходьте на наступний рівень, доки попередній не зелений.**
> Виняток лише один, він названий у §0.

Зворотний бік того ж правила: **не починайте з кінця**. Прогулянка
браузером по зламаному коду витрачає півгодини на те, що `pyflakes` каже
за секунду.

---

## §0. Перед усім: чи те ви взагалі перевіряєте

Дві хвилини, які рятують півдня.

```bash
git log --oneline -1          # той самий коміт, що ви думаєте?
git status --short            # немає незакомічених правок, які все пояснять?
```

І окремо — **чи розгорнуте те, що ви перевіряєте**. Тричі за цю програму
перевіряли інстанс, який не був тим, що чинили:

- на staging доказ прямий — вміст статики:
  `curl -s https://.../static/css/style.css | grep <ознака вашої зміни>`;
- на проді статика за HTTP Basic, тож прямого доказу немає: `/healthz`
  дає `uptime_seconds`, і свіжий процес — це непрямий доказ, не SHA.

Єдиний виняток із правила «не переходити далі»: якщо ви перевіряєте
**інфраструктуру** (деплой доїхав, БД жива), §0 і є вся перевірка.

---

## §1. Статичний аналіз — секунди

```bash
python -m pyflakes routes/*.py engine/*.py app.py mcp_server/*.py
```

**Чому першим.** Ловить клас помилок, який жоден тест не бачить:
`NameError` усередині широкого `except` не падає гучно — фіча просто не
відбувається, і всі тести зелені, бо ніхто її не перевіряв. Саме так
діагностика невдалого прогону не писалася жодного разу від дня написання.

Шукайте `undefined name`. Очікуване одне: `engine/qa_testers.py:747` —
рядкова анотація під `from __future__ import annotations`, хибне
спрацювання. Решта — дефект.

**Якщо червоно — стоп.** Далі немає сенсу: тест зелений на коді з
невизначеним іменем означає, що тест туди не заходить.

---

## §2. Unit — секунди, без БД і без HTTP

```bash
python -m pytest tests/ -q -k "not integration" -p no:randomly
```

Перевіряє **рішення**, а не маршрути: чи `is_admin()` каже «ні» плейн-юзеру,
чи `org_budget_state()` вважає «рівно на ліміті» перевищенням.

**Чому до інтеграційних.** Якщо функція, яку питає шаблон, відповідає
неправильно, інтеграційний тест теж упаде — але покаже вам 403 замість
«ось ця функція бреше». Діагностика на рівень точніша.

---

## §3. Integration — хвилини, БД + HTTP-клієнт

```bash
python -m pytest tests/ -q -p no:randomly
```

Ендпоінти, ролі, статус-коди, запис у БД.

**Що тут легко зіпсувати — і як не зіпсувати:**

1. **Перевіряйте статус явно.** `assert b"секрет" not in resp.data` —
   правда для будь-якої відмови, для 403 і для 500. Такий тест не може
   впасти й тому нічого не міряє. Спершу `assert resp.status_code == 403`.
2. **Знайте, ким ви залогінені.** Фікстура `client` у цьому наборі
   **уже залогінена адміном**. Тест, який «увійшов як user», але POST не
   спрацював, мовчки ходить адміном і повідомляє зворотне. Асертьте, що
   вхід стався.
3. **Не ганяйте набір паралельно із самим собою** — одна скретч-база й
   один каталог сесій. Дев'ять фальшивих падінь; та сама нога наодинці —
   зелена.

---

## §4. Functional — те, що людина справді бачить

Рендер, а не статус-код. Навігація, банери, наявність і відсутність.

**Головне: беріть той фрагмент сторінки, про який твердження.** Пошук
слова «Team» по всьому документу знайде його в тексті гіда й доповість про
пункт меню, якого немає. Виріжте `<ul class="nav-steps">` і дивіться там.

І завжди перевіряйте **обидва напрямки**. Правило, що ховає модуль від
усіх, пройде тест «користувач не бачить Team» і видалить продукт. Другий
тест — «адмін бачить» — коштує один рядок.

---

## §5. E2E — справжній браузер

```
preview_start → вхід через справжню форму → обхід
```

**Чому в кінці, а не замість усього.** E2E найповільніший і найгірше
діагностує: він каже «не працює», а не «ось цей рядок». Його цінність в
іншому — він єдиний бачить те, чого немає в жодному тесті: реальний
рендер, CSP, справжню сесію, справжній редірект.

Мінімум на кожну роль:

1. увійти **через форму** (не підкладати сесію — це вже робить §3);
2. звірити сайдбар зі списком того, що роль має бачити;
3. постукати в заборонені URL напряму — саме тут ховається «сховали
   посилання, а сторінка віддається»;
4. переконатися, що **робота, заради якої входять, ціла**: Test Cases,
   Checklist, Bug Reports відповідають 200.

---

## §6. CI — і чому локальне зелене його не замінює

```
push → дочекатися всіх перевірок → тільки потім мердж
```

Локально немає Postgres, а CI піднімає справжній; локально e2e один раз, у
CI — десять. Червона матриця вже стояла непоміченою чотири дні при 4 531
зелених локально.

І окремо: **мердж у `main` розгортає прод**. «На око безпечно» — це саме
те міркування, через яке ті чотири дні й сталися.

---

## §7. Після мерджу

1. CI перезапускається на `main` для того ж SHA — дочекайтеся;
2. перевірте, що деплой доїхав (§0);
3. якщо змінювали те, що видно користувачеві, — пройдіть §5 ще раз уже
   на розгорнутому інстансі. Локальний і розгорнутий стани розходяться
   через змінні оточення, і це видно тільки там.

---

## Коротко

| § | Рівень | Час | Ловить те, чого не ловить наступний |
|---|---|---|---|
| 0 | Що саме перевіряємо | 2 хв | перевірку не того інстансу |
| 1 | pyflakes | сек | `NameError` під широким `except` |
| 2 | Unit | сек | брехливе рішення, а не його наслідок |
| 3 | Integration | хв | ролі, коди, записи в БД |
| 4 | Functional | хв | що бачить людина, в обидва боки |
| 5 | E2E | хв | рендер, CSP, сесія, прямий URL |
| 6 | CI | ~10 хв | Postgres, десятикратний e2e |
| 7 | Після мерджу | — | розбіжність локального й розгорнутого |

Правило, яке варто запам'ятати замість усієї таблиці: **тест, який не може
впасти, — не доказ.** Якщо не впевнені, що перевірка справді щось міряє,
зламайте код навмисно й переконайтеся, що вона червоніє.
