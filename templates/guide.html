📖 TestForTge — User Guide

How to use every module of TestForTge end-to-end. Each section below covers what the module does, the typical workflow, the key controls, and the common mistakes that bite first-time users.

📊 Dashboard

The landing page. Shows your saved projects, live session metrics (test-case count, checklist items, execution ratios, bug severity, environments covered), and quick access to recent runs.

Typical workflow

  1. Pick or create a project. Every other module attaches its work to the active project. The sidebar shows the current project name; click "Projects" to switch.
  2. Skim the metrics. Pass-rate, bug severity distribution and environments covered tell you at a glance whether the last release was clean.
  3. Open the relevant module. Estimation for new scope, Test Cases for design, Test Execution for running, Bug Reports for triage.

Common mistakes

  • Not setting an active project before generating — artefacts go into a stand-in "Untitled" bucket and are harder to find later.

📈 Estimation

Produces a Min/Max QA effort breakdown plus a starter test- case set from one of three sources. Output: hours per phase (Test design · Execution · Regression · Bug reporting + buffer) and a one-platform vs full-compatibility roll-up with PERT confidence bands.

Three input tabs

  1. 📝 Requirements text. Paste a spec, user-story list, or feature backlog. The estimator normalises bullets / tables / freeform prose into a Feature list. You can also attach a .docx / .pdf / .xlsx — its text is merged with the textarea content. Best for: written specifications, BRD/PRD documents, transcribed kickoff notes.
  2. 🎨 Mockups. Upload PNG / JPG / WebP / PDF design screens (up to 20), or paste a public Figma file/frame URL. A vision model lists every testable element it sees — forms, dialogs, navigation, error states — and feeds them into the same estimator. Best for: design hand-off before code exists, visual-spec changes, third-party mockups.
  3. 🌐 URL crawl. Paste a production or staging URL. The crawler walks the site, identifies pages and forms, and infers the architecture (CMS / SPA / e-commerce). Best for: existing sites, re-estimation, competitor benchmarking.

Reading the result

  • The summary card shows total test cases, total feature hours, and the one-platform vs full-compatibility roll-ups. The "PERT confidence" panel under it is the statistical view; the headline numbers stay two-point.
  • The phase table breaks the total into Communication · Documentation review · Checklist creation · Functional/ UI · Bug reporting · Bug rechecking · Regression · Compatibility (per extra platform). Each row is editable via the coefficients above.
  • The history-calibration hint compares the current estimate against your past projects so you can spot outliers ("This is 1.8× your average for similar scope").

Convert estimate → real test cases

After the estimate renders, click "Generate test cases from this estimate →". The extracted feature list is pre-loaded into the Test Cases generator's input box; click Generate to materialise them.

Common mistakes

  • Switching tabs but leaving content in the previous tab — only the active tab's fields are submitted. Move your text/files to the right tab before clicking Run.
  • Bumping the buffer to 30%+ "just in case" — the PERT band already contains the variability. Stack on top only when you have a concrete reason (new tooling, unfamiliar domain, unreliable team).
  • For Mockups: needing more than 20 frames — split the run by epic / flow.
  • Figma URLs without a public link — only the cover image is fetched. Set FIGMA_PAT in env to enable the REST API path that pulls per-frame renders.

✅ Test Cases

Generates ISTQB-shaped test cases (id / section / summary / preconditions / steps / data / expected / category / type / priority / status) from requirements text. Saves to the active project automatically.

Typical workflow

  1. Paste requirements (or arrive prefilled from Estimation). Optionally attach .docx / .pdf / .xlsx / .csv / .md — text is extracted and merged.
  2. Add a custom prompt if you need a specific focus ("regression cases with form fills, submits and scrolls", "negative + edge cases only", "API only").
  3. Click Generate. The generator spawns a background job so the UI stays responsive; a progress modal polls until done.
  4. Review the result. Cases group by section. Use Export (top right) for .xlsx / .csv / .docx / Jira-XML.

Common mistakes

  • Vague input ("test the login page") → vague output ("verify login works"). Give the generator structure: list fields, paths, error messages, environment.
  • Re-running the same input expecting identical output — LLM generation is non-deterministic by design. Seed with the custom prompt for reproducibility.
  • Forgetting to save / export. The pack persists to the project's Postgres row, so it survives session wipes, but bookmarking the page won't preserve a custom prompt.
{# ─────────────────────────────────────────────────────────────── #}

📋 Checklist

High-level smoke checklist — broader strokes than test cases, suitable for sanity checks, exploratory rounds, and cross-team sign-off. Same input pattern as Test Cases but the LLM is prompted for objectives instead of detailed steps.

Typical workflow

  1. Drop your requirements / pasted text / attachment as on the Test Cases page.
  2. Tweak the custom prompt if you want a specific lens ("from a security perspective", "mobile-first", "regression-only").
  3. Generate. Items group by section, show a category (Positive / Negative / Edge / Security) and a one-line objective.
  4. Use Export for sharing with non-technical stakeholders — the XLSX is friendlier than a TC pack.

When to pick Checklist over Test Cases

  • Time-boxed exploratory testing.
  • Stakeholder demos / acceptance walk-throughs.
  • Smoke + sanity rounds on a release candidate.
  • You don't yet have detailed specs but need a structured coverage list.

▶️ Test Execution

Runs your TC pack against an environment. Two modes:

  1. Deterministic simulator (no Base URL): assigns Pass/Fail/Blocked using heuristics on the test case content. Fast, no browser needed.
  2. Real Playwright run (Base URL set): spawns a headless Chromium / Firefox / WebKit, executes the steps for real, captures per-step screenshots and optional video, and produces evidence for any failures.

Typical workflow

  1. Set the Base URL (top of Automation Configuration). Without it the run is simulator-only — no live preview, no screenshots, no bug-attached video.
  2. Pick the environment(s) — Web / Mobile Web / iOS / Android. Each one produces its own run record so you can compare side-by-side.
  3. Optionally open "Open live view in new tab" to watch the headless browser frame-by-frame.
  4. Click Run Test Execution. The form stays put and shows in-page progress; the Playwright pass runs as a fully detached subprocess so it survives any web-server restart.
  5. When the worker finishes, the page auto-imports results: gallery thumbnails, per-case Pass/Fail, and auto-generated bug reports for failures.

Reading screenshots

  • Passed TCs show the clean per-step "after" frames.
  • Failed TCs lead with the annotated failure screenshot (red box + arrow on the broken element) plus the previous step's frame for context.
  • Identical consecutive frames are deduped — a sequence like (click → expect_text → expect_url) on the same page becomes one thumbnail, not three.

If the run stalls

  • The recent runs table on /test-execution/live labels stalled runs with a red "stalled" badge (no info.json updates for >2 min — usually OOM-killed Chromium on the free tier).
  • Click Import partial to load whatever cases finished before the crash.

Common mistakes

  • Forgetting Base URL — the simulator runs and you wonder why the live view stays empty.
  • Running 100+ cases on the free tier — Chromium memory adds up and the dyno OOM-kills it. Split into batches of ≤62 or upgrade to a Render Background Worker.
  • Closing the browser tab before the worker finishes — harmless on its own (the worker is detached) but you lose the auto-redirect to results. Re-open /test-execution/live and use the recent runs table.

🐞 Bug Reports

ISTQB-aligned, Jira-friendly defect store. Bugs are created automatically from Failed/Blocked test executions and can also be added manually.

What's in a bug

  • Title — "[Component]: [Observable defect]" format. Phrases like "does not work as expected" are stripped automatically.
  • Description — 2-5 sentence narrative, third-person, observable language only.
  • Steps to Reproduce — numbered atomic steps starting from "1. Navigate to <URL>".
  • Actual Result — observable state plus the verbatim Playwright error if available.
  • Expected Result — "should" phrasing.
  • Severity / Priority / Frequency — heuristically derived from the defect class (click_timeout, text_assertion_fail, etc.). Bumped to Critical/Highest when the affected area is a core path (login, checkout, search).
  • Attachments — the FAILED step's annotated screenshot + the prior step's frame for context, plus the recorded video when present.

Typical workflow

  1. After a run, open Bug Reports — auto-generated bugs sit there with linked test-case IDs.
  2. Click a bug to expand. The screenshot above shows exactly where the run broke.
  3. Triage: bump priority/severity if the heuristic misjudged, assign to a developer, add labels.
  4. Export to Jira (XML) when ready to hand off.

Common mistakes

  • Creating a manual bug without preconditions / steps — the form accepts it but the export is awkward. Aim for ISTQB minimum: title, severity, repro steps, AR, ER.
  • Trusting the auto-generated severity blindly — review and adjust based on business context the heuristic can't see.

💬 Tedgie chat

The TestForTge AI assistant. Tedgie answers questions about the app's modules, can analyse your saved test cases / checklist / bug reports, and runs ad-hoc QA reasoning ("what risks does this scope create?", "what's missing from this checklist?").

What Tedgie is good at

  • "Why is my live view empty?" → Tedgie walks the diag checklist (Base URL set? Playwright importable? screenshots writing?).
  • "Summarise the last 10 bugs by component." → Tedgie reads your session bugs and groups them.
  • "Suggest 5 negative cases I'm missing for the login flow." → Tedgie generates targeted ideas from the current TC pack.

What Tedgie is NOT

  • A test runner — use Test Execution.
  • An estimation engine — use Estimation.
  • An autonomous agent — Tedgie answers questions and generates content, but doesn't click buttons in your app for you.

💡 Pro tips that save hours

  • Use the project picker. Pinning an active project means every TC, run, and bug auto-attaches there. Survives Render dyno restarts.
  • Start at Estimation, not Test Cases. Even when you have a clear scope, running the estimator first surfaces edge cases you'd otherwise miss in TC generation.
  • Set Base URL even on the simulator path. It enables real-site checks (HTTP probes, header validation) that catch bugs the simulator can't see.
  • Open Live view in a separate tab when running >30 cases. Watching frame-by-frame is usually how you spot WHY a run stalled.
  • Export to .xlsx for stakeholders, .docx for documentation, Jira-XML for engineering. All three exports preserve the same data.
  • Use the Bug Reports tabs (severity / priority / status) to triage. The auto-bugs land Open; move them through the workflow as they're worked.
